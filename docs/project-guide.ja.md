# Keras 回帰モデル — プロジェクトガイド

[ドキュメント索引](README.md) | [English](project-guide.en.md) | [한국어](project-guide.ko.md) | 日本語

## 1. プロジェクト概要

このプロジェクトは TensorFlow と Keras を使用してコンクリートの圧縮強度を予測します。IBM/CognitiveClass のディープラーニング演習を出発点とし、ノートブック形式のサンプルを再利用可能な Python コマンドラインプロジェクトへ再構成しました。

このリポジトリでは、次の 2 つのエンジニアリング領域を扱います。

1. **AI/ML エンジニアリング** — データ準備、ニューラルネットワーク回帰、アーキテクチャ実験、学習、評価指標、可視化
2. **エージェント支援ソフトウェアエンジニアリング** — コーディングエージェントを利用した要件確認、コードレビュー、リスク特定、技術判断の文書化、限定的な変更、SDLC 支援

ニューラルネットワーク自体を自律エージェントとして扱っているわけではありません。エージェント的な要素は、ML システムを取り巻く開発・レビューのワークフローにあります。

## 2. データセット

IBM CognitiveClass のコンクリート強度データセットを使用します。

### 入力変数

- Cement
- Blast furnace slag
- Fly ash
- Water
- Superplasticizer
- Coarse aggregate
- Fine aggregate
- Age

### 目的変数

- コンクリート圧縮強度

現在の実装では、学習前に入力変数を平均がおよそ 0、標準偏差がおよそ 1 になるよう標準化します。

## 3. モデルアーキテクチャ

2 種類のフィードフォワード回帰モデルを用意しています。

### Base model

```text
8 inputs
  -> Dense(50, ReLU)
  -> Dense(50, ReLU)
  -> Dense(1)
```

### Deep model

```text
8 inputs
  -> Dense(50, ReLU)
  -> Dense(50, ReLU)
  -> Dense(50, ReLU)
  -> Dense(50, ReLU)
  -> Dense(50, ReLU)
  -> Dense(1)
```

両モデルで共通して使用する要素:

- TensorFlow/Keras `Sequential`
- 隠れ層の ReLU 活性化関数
- 連続値回帰用の線形出力ニューロン 1 個
- Adam オプティマイザ
- 平均二乗誤差（MSE）損失

アーキテクチャは `build_model()` を通じてパラメータ化されているため、学習パイプラインを書き直さずにモデルの深さを変更できます。

## 5. ローカルセットアップ

```bash
pipenv --python 3.11 install
pipenv shell
```

シェルに入らない場合は、各コマンドの先頭に `pipenv run` を付けて実行できます。

### Base model の学習

```bash
pipenv run python regression_models.py --model base --epochs 100 --val-split 0.3
```

### Deep model の学習

```bash
pipenv run python regression_models.py --model deep --epochs 150 --val-split 0.2
```

### バッチサイズの指定

```bash
pipenv run python regression_models.py --batch-size 32
```

### 可視化の生成

```bash
pipenv run python visualize_data.py --output-dir figures
```

可視化スクリプトは、ヒストグラム、相関ヒートマップ、各入力変数と Strength の散布図を生成します。

## 6. エージェント支援 SDLC

コーディングエージェントは、ソフトウェア開発ライフサイクル全体でエンジニアリングの協力者として使用します。生成されたコードを無条件に信用することはなく、プロジェクト目標をエージェント自身に再定義させることもありません。

通常のワークフローは次の通りです。

```text
要件
   ↓
エージェント支援分析
   ↓
GitHub Issue + 受け入れ基準
   ↓
専用ブランチ
   ↓
範囲を限定したコードまたは文書変更
   ↓
Diff / モデル / テスト検証
   ↓
Pull Request
   ↓
人によるレビューと判断
   ↓
Merge + ドキュメント更新
```

### 要件分析

エージェントは、抽象的な目標を具体的なエンジニアリングタスクと受け入れ基準に分解する支援を行います。例:

- モデルアーキテクチャの文書化
- コードと文書の不一致の特定
- 前処理方法のレビュー
- テストや再現性管理の不足の検出
- 限定的なリファクタリングの提案

最終的な要件とスコープは人が管理します。

### Issue の作成

重要な変更は、可能な限り GitHub Issue から開始します。Issue には次を記録します。

- 問題または目標
- スコープ
- 受け入れ基準
- 既知のリスク
- 完了を示す証拠

これにより、実装前から変更の追跡可能性を確保できます。

### ブランチ戦略

重要な作業は `main` を直接変更せず、専用ブランチで行います。

一般的なブランチ名:

```text
docs/...
fix/...
feature/...
refactor/...
```

### 実装

要件が明確になった後、コーディングエージェントが範囲の限定された変更を支援できます。エージェントが生成した変更は、人間のエンジニアによる変更と同様にレビュー・検証します。

### 検証

コードが実行できるという理由だけで、エージェント自身に完了判定をさせません。

検証には次のような作業を含めます。

- Git diff の確認
- 学習スクリプトの実行
- training loss と validation loss の比較
- 生成されたグラフの確認
- import と CLI 動作の確認
- ドキュメントとソースコードの整合性確認
- 自動テストの実行
- 受け入れ基準の充足確認

### Pull Request

Pull Request を主なレビュー境界として使用します。PR には次を記述します。

- 何を変更したか
- なぜ変更したか
- どの Issue に対応するか
- どのように検証したか
- どの制限事項が残っているか

レビューされ、受け入れられた変更のみ `main` にマージします。

## 7. コーディングエージェントの観察と品質評価

エージェントの活動は、チャット履歴だけではなく、レビュー可能なエンジニアリング成果物として残すことを重視します。

有用な証拠には次が含まれます。

- Issue の説明
- 受け入れ基準
- ブランチのコミット
- ファイル diff
- Pull Request の説明
- 必要に応じたコードコメント
- モデル出力と評価指標
- テスト出力
- 更新されたドキュメント

結果の品質は次の観点で評価します。

1. 元の要件を満たしているか
2. 意図したアーキテクチャを維持しているか
3. 技術的に正しいか
4. 再現可能か
5. 証拠によって裏付けられているか
6. 残っている不確実性を正直に文書化しているか

## 8. ML 方法論と品質ゲート

コーディングエージェントが ML 上のリスクを発見することはできますが、統計的な妥当性は独立して検証する必要があります。

現在の主なレビュー項目は次の通りです。

### 前処理におけるデータリーク

現在のコードでは、Keras が validation split を作成する前にデータセット全体の統計値で標準化を行っています。そのため validation データの情報が前処理統計に含まれます。より厳密なパイプラインでは、先に train/validation/test に分割し、学習データのみから前処理統計を算出して他のデータに適用します。

### 検証戦略

現在は Keras の `validation_split` を使用しています。より明確で再現しやすい評価を行うには、明示的なランダム train/validation/test split を採用する方が望ましいです。

### 深いモデルが自動的に優れているわけではない

Deep model は Base model より表現力がありますが、汎化性能が改善する場合にのみ有用です。アーキテクチャ比較は training loss だけでなく、保持された評価データの指標で判断する必要があります。

### 再現性

ニューラルネットワークの単一実行結果は、重み初期化やデータ順序の影響を受けます。アーキテクチャを比較する場合は、必要に応じて固定 seed や複数回の実験を使用します。

## 9. 今後推奨する評価指標

現在のプロジェクトでは training MSE と validation MSE を出力します。今後は以下の追加を推奨します。

- test MSE
- root mean squared error (RMSE)
- mean absolute error (MAE)
- coefficient of determination (R²)
- actual vs predicted plot
- residual plot
- 複数回実行の平均値と標準偏差

これらを使用することで、エージェントが提案した ML 変更が本当にモデル改善につながったかを判断しやすくなります。

## 10. ドキュメント方針

ドキュメントは SDLC の一部であり、最後に追加するだけの作業ではありません。

重要な変更では:

- 関連する技術文書を同じ PR で更新する
- コード例が実行可能であることを確認する
- 現在の実装と将来計画を明確に区別する
- 既知の制限を隠さず記録する
- 共通のプロジェクト動作に影響する場合は英語、韓国語、日本語の文書を同時に更新する

技術用語については英語版を基準とします。API 名、Python 識別子、ファイル名、コマンドは翻訳せず原文を維持します。

## 11. 現時点での学び

このプロジェクトから得た主な学び:

- ML コードが正常に動作しても、評価方法に問題が残る場合がある
- ドキュメントは実際のソースコードと照合して検証する必要がある
- 大きなニューラルネットワークが常に優れたモデルとは限らない
- コーディングエージェントは追跡可能なエンジニアリングプロセスの中で使用すると最も価値が高い
- Issue、branch、PR、メトリクス、文書によってエージェント支援作業を監査可能にできる
- アーキテクチャ、統計的方法、最終承認には人間によるレビューが重要

## 12. プロジェクトの方向性

このリポジトリは、小さく理解しやすい構成を維持しながら、プロフェッショナルな AI エンジニアリングの例として改善していくことを目標としています。

短期的な優先事項:

1. train/validation/test 分割の改善
2. 前処理データリークの解消
3. より強力な回帰評価指標の追加
4. 再現可能な自動テストの追加
5. 重要な変更で issue/branch/PR の追跡性を維持
6. 英語・韓国語・日本語ドキュメントの同期維持

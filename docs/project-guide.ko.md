# Keras 회귀 모델 — 프로젝트 가이드

[문서 인덱스](README.md) | [English](project-guide.en.md) | 한국어 | [日本語](project-guide.ja.md)

## 1. 프로젝트 개요

이 프로젝트는 TensorFlow와 Keras를 사용하여 콘크리트 압축 강도를 예측합니다. IBM/CognitiveClass의 딥러닝 실습에서 시작했으며, 노트북 중심의 예제를 재사용 가능한 Python 명령줄 프로젝트로 재구성했습니다.

이 저장소는 두 가지 엔지니어링 영역을 함께 보여 줍니다.

1. **AI/ML 엔지니어링** — 데이터 준비, 신경망 회귀, 모델 구조 실험, 학습, 지표, 시각화
2. **에이전트 지원 소프트웨어 엔지니어링** — 코딩 에이전트가 요구사항 검토, 코드 리뷰, 위험 식별, 기술 의사결정 문서화, 제한된 변경 수행, SDLC 지원에 참여

신경망 자체를 자율 에이전트라고 설명하지 않습니다. 에이전트적인 요소는 ML 시스템을 개발하고 검토하는 소프트웨어 개발 워크플로에 있습니다.

## 2. 데이터셋

이 프로젝트는 IBM CognitiveClass 콘크리트 강도 데이터셋을 사용합니다.

### 입력 변수

- Cement
- Blast furnace slag
- Fly ash
- Water
- Superplasticizer
- Coarse aggregate
- Fine aggregate
- Age

### 목표 변수

- 콘크리트 압축 강도

현재 구현에서는 학습 전에 입력 변수를 평균이 약 0, 표준편차가 약 1이 되도록 표준화합니다.

## 3. 모델 구조

프로젝트는 두 개의 피드포워드 회귀 모델 구조를 제공합니다.

### 기본 모델

```text
8 inputs
  -> Dense(50, ReLU)
  -> Dense(50, ReLU)
  -> Dense(1)
```

### 심층 모델

```text
8 inputs
  -> Dense(50, ReLU)
  -> Dense(50, ReLU)
  -> Dense(50, ReLU)
  -> Dense(50, ReLU)
  -> Dense(50, ReLU)
  -> Dense(1)
```

두 모델 모두 다음을 사용합니다.

- TensorFlow/Keras `Sequential`
- 은닉층 ReLU 활성화 함수
- 연속값 회귀를 위한 하나의 선형 출력 뉴런
- Adam 옵티마이저
- 평균제곱오차(MSE) 손실 함수

모델 구조는 `build_model()`을 통해 매개변수화되어 있으므로 학습 파이프라인 전체를 다시 작성하지 않고도 깊이를 변경할 수 있습니다.

## 5. 로컬 설정

```bash
pipenv --python 3.11 install
pipenv shell
```

쉘에 진입하지 않는 경우 각 명령 앞에 `pipenv run`을 붙일 수 있습니다.

### 기본 모델 학습

```bash
pipenv run python regression_models.py --model base --epochs 100 --val-split 0.3
```

### 심층 모델 학습

```bash
pipenv run python regression_models.py --model deep --epochs 150 --val-split 0.2
```

### 배치 크기 지정

```bash
pipenv run python regression_models.py --batch-size 32
```

### 시각화 생성

```bash
pipenv run python visualize_data.py --output-dir figures
```

시각화 스크립트는 히스토그램, 상관관계 히트맵, 입력 변수와 강도 간의 산점도를 생성합니다.

## 6. 에이전트 지원 SDLC

코딩 에이전트는 소프트웨어 개발 생명주기 전반에서 엔지니어링 협업 도구로 사용됩니다. 에이전트가 생성한 코드를 무조건 신뢰하지 않으며, 프로젝트 목표를 독자적으로 재정의하도록 두지 않습니다.

일반적인 워크플로는 다음과 같습니다.

```text
요구사항
   ↓
에이전트 지원 분석
   ↓
GitHub 이슈 + 승인 기준
   ↓
전용 브랜치
   ↓
범위가 제한된 코드 또는 문서 변경
   ↓
Diff / 모델 / 테스트 검증
   ↓
Pull Request
   ↓
사람의 리뷰 및 판단
   ↓
Merge + 문서 업데이트
```

### 요구사항 분석

에이전트는 넓은 목표를 구체적인 엔지니어링 작업과 승인 기준으로 나누는 데 도움을 줄 수 있습니다. 예시는 다음과 같습니다.

- 모델 구조 문서화
- 코드와 문서 간 불일치 식별
- 전처리 방법 검토
- 테스트 또는 재현성 관리의 누락 확인
- 제한된 리팩터링 제안

최종 요구사항과 범위는 사람이 관리합니다.

### 이슈 생성

중요한 변경은 가능하면 GitHub 이슈에서 시작합니다. 이슈에는 다음을 기록합니다.

- 문제 또는 목표
- 범위
- 승인 기준
- 알려진 위험
- 완료를 증명할 근거

이를 통해 구현 전에 추적 가능성을 확보합니다.

### 브랜치 전략

중요한 변경은 `main`에서 직접 작업하지 않고 전용 브랜치에서 수행합니다.

일반적인 브랜치 이름 예시:

```text
docs/...
fix/...
feature/...
refactor/...
```

### 구현

요구사항이 명확해지면 코딩 에이전트가 범위가 제한된 변경을 수행하도록 지원할 수 있습니다. 에이전트가 만든 변경은 다른 엔지니어의 기여와 동일하게 검토하고 검증합니다.

### 검증

코드가 실행된다는 이유만으로 에이전트가 자신의 작업을 완료로 판단하게 두지 않습니다.

검증에는 다음이 포함될 수 있습니다.

- Git diff 검토
- 학습 스크립트 실행
- 학습 손실과 검증 손실 비교
- 생성된 그래프 검토
- import 및 CLI 동작 확인
- 문서가 실제 소스 코드와 일치하는지 확인
- 자동화 테스트 실행
- 승인 기준 충족 여부 확인

### Pull Request

Pull Request는 주요 리뷰 경계입니다. PR에는 다음을 설명해야 합니다.

- 무엇이 변경되었는지
- 왜 변경했는지
- 어떤 이슈를 해결하는지
- 어떻게 검증했는지
- 남아 있는 제한사항은 무엇인지

리뷰와 승인을 거친 변경만 `main`에 병합합니다.

## 7. 코딩 에이전트 작업 관찰 및 품질 평가

에이전트의 작업은 단순한 채팅 기록이 아니라 검토 가능한 엔지니어링 산출물로 남아야 합니다.

유용한 근거는 다음과 같습니다.

- 이슈 설명
- 승인 기준
- 브랜치 커밋
- 파일 diff
- Pull Request 설명
- 필요한 경우 코드 주석
- 모델 출력 및 지표
- 테스트 출력
- 업데이트된 문서

결과의 품질은 다음 질문으로 평가합니다.

1. 원래 요구사항을 충족하는가?
2. 의도한 아키텍처를 유지하는가?
3. 기술적으로 올바른가?
4. 재현 가능한가?
5. 근거로 뒷받침되는가?
6. 남아 있는 불확실성을 정직하게 문서화했는가?

## 8. ML 방법론 및 품질 기준

코딩 에이전트가 ML 관련 위험을 식별할 수는 있지만, 통계적 타당성은 별도로 검증해야 합니다.

현재 검토 대상은 다음과 같습니다.

### 전처리 데이터 누수

현재 코드는 Keras가 검증 데이터를 나누기 전에 전체 데이터셋의 통계로 정규화를 수행합니다. 따라서 검증 데이터의 정보가 정규화 통계에 일부 반영됩니다. 더 강한 파이프라인에서는 먼저 데이터를 학습/검증/테스트로 나눈 뒤, 학습 데이터만으로 전처리 통계를 계산하고 나머지 데이터에 적용해야 합니다.

### 검증 전략

현재 프로젝트는 Keras의 `validation_split`을 사용합니다. 더 명확하고 재현 가능한 평가를 위해서는 명시적인 무작위 train/validation/test split을 사용하는 것이 좋습니다.

### 더 깊은 모델이 항상 더 좋은 것은 아님

심층 모델은 기본 모델보다 용량이 크지만, 실제로 일반화 성능이 개선될 때만 가치가 있습니다. 모델 구조 비교는 학습 손실만이 아니라 보류 데이터의 평가 지표를 기준으로 해야 합니다.

### 재현성

신경망의 단일 실행 결과는 가중치 초기화와 데이터 순서의 영향을 받을 수 있습니다. 구조 비교 시에는 필요한 경우 고정된 seed와 반복 실험을 사용해야 합니다.

## 9. 향후 권장 평가 지표

현재 프로젝트는 학습 및 검증 MSE를 출력합니다. 향후 다음 지표를 추가하는 것이 좋습니다.

- test MSE
- root mean squared error (RMSE)
- mean absolute error (MAE)
- coefficient of determination (R²)
- 실제값 대 예측값 그래프
- residual plot
- 반복 실행의 평균 및 표준편차

이러한 지표는 에이전트가 제안한 ML 변경이 실제로 모델을 개선했는지 판단하는 데 도움이 됩니다.

## 10. 문서화 정책

문서화는 SDLC의 일부이며 마지막에 추가하는 작업이 아닙니다.

중요한 변경의 경우:

- 관련 기술 문서를 같은 PR에서 업데이트합니다.
- 코드 예제가 실제로 실행 가능한지 확인합니다.
- 현재 구현과 향후 계획을 명확히 구분합니다.
- 알려진 제한사항을 숨기지 않고 기록합니다.
- 공통 동작에 영향을 주는 변경은 영어, 한국어, 일본어 문서를 함께 업데이트합니다.

영어 문서를 기술 용어의 기준 버전으로 사용합니다. API 이름, Python 식별자, 파일명, 명령어는 번역하지 않고 원문을 유지합니다.

## 11. 현재까지의 교훈

이 프로젝트를 통해 다음과 같은 점을 확인했습니다.

- ML 코드는 정상 실행되어도 평가 방법론에 문제가 있을 수 있습니다.
- 문서는 실제 소스 코드와 대조하여 검증해야 합니다.
- 더 큰 신경망이 항상 더 좋은 모델은 아닙니다.
- 코딩 에이전트는 추적 가능한 엔지니어링 프로세스 안에서 사용할 때 가장 큰 가치를 제공합니다.
- 이슈, 브랜치, PR, 지표, 문서화를 통해 에이전트 지원 작업을 감사 가능하게 만들 수 있습니다.
- 아키텍처, 통계 방법론, 최종 승인에는 사람의 리뷰가 중요합니다.

## 12. 프로젝트 방향

이 저장소의 목표는 작고 이해하기 쉬운 구조를 유지하면서 전문적인 AI 엔지니어링 예제로 발전시키는 것입니다.

단기 우선순위는 다음과 같습니다.

1. train/validation/test 분리 개선
2. 전처리 데이터 누수 제거
3. 더 강한 회귀 평가 지표 추가
4. 반복 가능한 자동화 테스트 추가
5. 중요한 변경에 대해 issue/branch/PR 추적성 유지
6. 영어, 한국어, 일본어 문서를 함께 유지
